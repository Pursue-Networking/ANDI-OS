# ANDI PLAN, 07 JULY 2026

What we are building, how it should work, and how we will build it. Written in simple words. Sources: `docs/pdfs/KolinClientDiscovery.pdf`, `docs/pdfs/PursueNetworking_Milestones.pdf`, and the old code notes in `ABSOLV/` (reference only, we write everything from scratch).

## THE IDEA IN ONE PARAGRAPH

ANDI is an AI assistant that helps one person take care of their professional network. It reads the data the user already has (Gmail, Google Calendar, and LinkedIn exports), builds a memory of every contact, and every day answers three questions: Who should I reach out to? Why now? What should I say? It shows a ranked contact list, a short morning brief, a profile page (dossier) for each contact, and a ready email draft written in the user's own voice. ANDI never sends anything by itself. The user reads, edits, and approves every message. That rule is fixed for version one.

## THE PROBLEM IT SOLVES

The user's relationship history is spread across email threads, meetings, LinkedIn chats, and memory. Keeping up with 100 plus people by hand is not possible. Good contacts go cold, follow ups are forgotten, and chances are missed. ANDI turns that scattered data into a short daily list of actions with a draft attached, so keeping the network warm takes minutes, not hours.

## WHAT THE END PRODUCT LOOKS LIKE

At the end of Milestone 5 we ship a controlled beta, not a public app.

- A hosted backend (runs on a server, not a laptop) that ingests data, scores contacts, and generates briefs, dossiers, and drafts.
- A small web dashboard where the user can:
  - Connect Gmail and Calendar, and upload a LinkedIn export.
  - See the ranked contact list (top 100 to 150 relationships).
  - Read the morning brief with a reason for every item.
  - Open a dossier for any contact.
  - Review a draft, then approve, edit, reject, or defer it.
  - Give feedback (useful, not relevant, wrong timing).
- Each user's data is fully separated from every other user.
- A delete or disconnect flow that removes the user's data.
- A monitoring view for us: cost per user, token use, errors, latency.
- Docs: onboarding guide, known limits, and an operations runbook.

Not in version one: auto sending, mobile app, polished consumer UI, HubSpot, Slack, Zoom, Outlook, a public API or public MCP package, and model fine tuning. ANDI may use open source models internally, but ANDI itself is a private product.

## HOW IT WORKS, STEP BY STEP

The system is one repeating loop:

1. INGEST. Pull Gmail threads, Calendar events, and LinkedIn export data through our private connectors. Store the raw records per user. This layer costs no AI money.
2. CLEAN AND LINK. Normalize names, emails, and timestamps. Merge duplicates (the same person in email, calendar, and LinkedIn becomes one contact). Filter bots and newsletters with plain rules, no AI. Keep a cursor so re runs only process new data, and a big ingestion job can resume after a crash without duplicates.
3. BUILD THE GRAPH AND MEMORY. Create the Contact Knowledge Graph with tier 1 (close), tier 2 (medium), tier 3 (weak) relationships. Chunk and embed the text into a search index so ANDI can find relevant history fast (pgvector). Keep a per contact memory that grows over time.
4. DETECT SIGNALS. Find events that matter: unanswered message, meeting coming up, meeting with no follow up, contact gone quiet, keyword hits, job change. Simple triage rules decide promote, skip, or hold before any AI call, which keeps cost low.
5. SCORE. Give each contact a network score built from subscores: email engagement, calendar meetings, LinkedIn activity, and ANDI specific signals (recency, frequency, response pattern, user marked importance). Signals get a priority score too: urgency, value, freshness, confidence.
6. PLAN AND GENERATE. For the top signals, pick a next best action (reconnect, follow up, thank you, intro request, reminder, or no action). Then generate the outputs: the morning brief, dossiers, and drafts. Every factual claim must point back to a source record (an email, an event, a LinkedIn line, or a note). If evidence is missing the output says unknown instead of making something up.
7. USER REVIEW. The user sees the item, the reason, the confidence level, the sources, and the draft. They approve, edit, reject, or defer. Nothing leaves the system without approval.
8. LEARN. Log the outcome. Approvals, edits, and rejections tune future scoring, timing, and writing style.

## FEATURES AND HOW EACH ONE WORKS

### 1. DATA INGESTION (MILESTONE 1)

- Gmail: list threads, fetch bodies, strip HTML and quoted replies, dedupe, store per user. Handles pagination, rate limits, and retries.
- Calendar: fetch events, attendees, times, recurrence. Link attendees to contacts. Do a deep backfill of history on first sync, old meetings are gold for relationship discovery.
- LinkedIn: import from CSV or data export and normalize it. We do not depend on live LinkedIn automation. If direct access ever works, fine, but the fallback is the plan.
- Ingestion runs on a schedule (daily, weekly, or manual) and prints a report: processed, skipped, duplicates, failures.
- Also here: the Gmail draft foundation, code that can create and update drafts in the user's Gmail without ever sending.

### 2. CONTACT KNOWLEDGE GRAPH (MILESTONE 1)

One record per real person, built by merging email, calendar, and LinkedIn records. Each contact gets a tier (1, 2, 3). Bot and newsletter senders are filtered with deterministic rules, target below 2 percent false positives checked against a hand labeled sample.

### 3. SEARCH INDEX AND MEMORY (MILESTONE 1)

All useful text is chunked, embedded, and stored in PostgreSQL with pgvector. This lets every later feature ask "what do we know about this person" and get real snippets back with IDs we can cite.

### 4. SCORING AND SIGNALS (MILESTONE 2)

- Network score per contact from the subscores above. Calibrated by labeling at least 100 contacts and reviewing the top 50 with the user. Target: 80 percent reviewer agreement on the top 20, 90 percent triage agreement on the label set.
- Signal taxonomy: what counts as useful, weak, duplicate, irrelevant, or false.
- Seven triage rules (promote, skip, hold) run before any AI spend.
- Tier boundaries adapt when the contact volume changes by more than 20 percent.

### 5. MORNING BRIEF (MILESTONE 2)

A short ranked list generated daily. Each item shows what happened, why it matters, and links to sources. Target: fewer than 3 false positive items per day. Every promoted item carries a one line explanation.

### 6. EVALUATION HARNESS (MILESTONE 2, USED FOREVER)

A four layer test bench: extraction accuracy, scoring precision, triage recall, brief relevance. It runs on every meaningful change and saves the output, so we always know if a prompt or model change made things worse. Cost per contact and cost per brief are measured here too.

### 7. PRIVATE INTEGRATION LAYER (MILESTONE 3)

The clean private interface between ANDI and outside services. Per our convention it lives in `mcp/`, one folder per source (gmail, calendar, linkedin). Each connector documents its tools, inputs, outputs, errors, retries, and auth. Includes integration tests and a security checklist (no leaked keys, no unsafe logs) before real user data touches it. This layer is private. It is not a public package and we make no open source claims about it.

### 8. DOSSIERS (MILESTONE 4)

A profile page per contact with fixed fields: identity, tier, relationship summary, recent interactions, open loops, opportunities, recommended next action, risks, confidence labels, and source references. Two formats: v4 structured (machine checkable) and v5 narrative (reads like an analyst note but maps back to the same fields). Targets: 95 percent of dossiers have all required fields, 90 percent of factual claims cite a source, under 5 percent unsupported claims. Missing data is shown as unknown, never invented.

### 9. PATCH SYSTEM (MILESTONE 4)

Small targeted updates instead of regenerating a whole dossier. Patch types: style, factual, risk, talking points, tone, relationship context. Each patch touches one section, is logged with before and after, and cannot remove citations or change unrelated text. This keeps outputs fresh and cheap.

### 10. DRAFT WRITING WITH VOICE PROFILE (MILESTONE 4)

- Draft types: follow up, check in, intro request, meeting recap, thank you, soft reactivation.
- A voice profile is built from the user's approved writing samples: greeting style, sentence length, warmth, sign off, formality, plus a banned phrases list.
- Facts and style are kept separate, so the voice layer cannot invent facts.
- Quality gate: a 20 draft human review set scored on a written 1 to 10 rubric. Average must be 7 or higher, and no draft passes with a false claim or pushy language.
- Every draft stays a draft until the user approves it.

### 11. SOURCE SUPPORT REVIEW (MILESTONE 4)

An automatic checker that compares every generated claim against the stored sources and marks it supported, partially supported, unsupported, stale, or ambiguous. Unsupported claims get blocked or flagged before the user sees them. This is the anti hallucination gate and it is a hard rule, not a preference.

### 12. COST CONTROL (MILESTONES 2, 4, 5)

- Track cost per contact, brief, dossier, draft, and user from day one.
- Rules before AI everywhere. Cheap model for extraction, better model only for synthesis. Batch jobs where latency does not matter. Cache what does not change.
- Milestone 4 targets: cut token use at least 15 percent (stretch 20) with no quality loss, and benchmark at least one extraction task on an open source model to see if it is worth using.
- Practical caps like a limit on drafts per day keep spend predictable. The old project aimed under about 6 dollars per user per month. Good habit to keep.

### 13. BETA PRODUCT (MILESTONE 5)

Final data structure cleanup, strict per user separation (tested, including two users who know the same person), hosted deployment with secrets outside the code, monitoring, deletion and disconnect flow, runbook, onboarding guide, the minimum dashboard described above, and a real validation run with an approved beta user.

## SAFETY AND PRIVACY RULES (NEVER BREAK)

- No email, message, or outreach is ever sent automatically. Drafts only, user approval required.
- No secrets in the codebase. Keys live in environment config or a credentials manager.
- One user's data never appears in another user's workflow.
- Claims must trace to sources. Missing evidence means saying unknown.
- Deletion and retention behavior is documented and tested before any external beta user joins.
- Logs avoid sensitive message content unless there is a clear need and access control.
- ANDI is not an open source product. Only the models or libraries it uses may be open source.

## HOW WE USE THE OLD ABSOLV CODE

Kolin's old build (see `ABSOLV/PROJECT-ANALYSIS.md` and `ABSOLV/schema.sql`) proved this product can work. We may read it as reference but every line we ship is written from scratch in this repo.

Ideas worth copying:

- Three tier data model: raw (free), linkage (free), derived (paid AI). It makes cost visible by design.
- Deterministic first: rules for triage, bot filtering, and lookups, AI only for extraction and writing.
- Citation check as a hard gate on every user facing claim.
- Cursors plus resumable walkers so big syncs survive crashes without duplicates.
- The patch idea: many small cacheable updates instead of one big regeneration.
- Simple in process scheduler (their APScheduler crons) instead of heavy queue systems.
- Voice profile from the user's own sent mail.
- Hard caps, like 5 drafts per day.

Mistakes to avoid this time:

- Do not keep two dossier versions alive for long. Pick one shape early.
- No prototype or spike code left in the main app.
- No temporary table name prefixes. Design the per user schema properly in Milestone 1.
- Do not cap history (their 30 threads per contact limit hurt quality). Plan full backfill with batch jobs.
- Schedule background jobs from the start instead of leaving them as manual CLI scripts.

## SUGGESTED TECH STACK

Simple and boring on purpose. Final call is the team's.

- Backend: Python with FastAPI.
- Database: PostgreSQL with pgvector (one database for data and search, nothing extra to sync).
- Jobs: APScheduler inside the app for crons and queues. No Redis or Celery until we truly need them.
- Connectors: MCP servers in `mcp/gmail`, `mcp/calendar`, `mcp/linkedin` with OAuth for Google.
- AI: hosted API models. Cheap model for extraction and classification, stronger model for dossiers and drafts, embeddings for search. Benchmark an open source model in Milestone 4.
- Dashboard (Milestone 5): a light Next.js app. Nothing fancy, review and approve is the whole job.
